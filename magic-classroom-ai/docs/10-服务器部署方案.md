# Magic Classroom AI — 服务器与部署方案

## 1. 原则
服务器规格必须按真实并发、课程素材体积和 AI 任务量决定，不按“注册用户数”简单换算。前期优先使用托管服务，减少运维负担。

## 2. Demo 阶段
不需要独立服务器。

建议：
- 前端：Vercel / Cloudflare Pages / Netlify。
- 数据：本地 JSON。
- 素材：静态 CDN 或部署平台静态资源。

目标：快速提供领导可访问链接。

## 3. 单校 MVP
建议起步：
- Web：静态托管 + CDN。
- API：4 vCPU / 8 GB RAM。
- PostgreSQL：托管数据库 2~4 vCPU / 4~8 GB。
- 对象存储：按实际素材量购买。
- Redis：如果尚未使用队列/缓存可暂缓。

此规格仅作为起点，必须结合监控和压测调整。

## 4. 多校阶段
架构：
- 负载均衡。
- 2 台以上无状态 API 实例。
- 托管 PostgreSQL 高可用。
- Redis/消息队列用于 AI Job。
- 独立 Worker。
- 对象存储 + CDN。

## 5. AI Worker
AI 生成不与普通 API 共用耗时任务线程。

```text
API -> Job Queue -> Worker -> AI Provider -> Validate -> DB
```

Worker 可根据任务积压水平单独扩容。

## 6. 媒体存储
图片、音频、视频放对象存储。

不要：
- 长期存服务器本地磁盘。
- 把大视频放数据库。
- 把所有媒体打包进前端 bundle。

## 7. CDN
课程发布后：
- 图片/音频/视频走 CDN。
- Published Course JSON 可缓存。
- 编辑草稿接口不使用长期 CDN 缓存。

## 8. 域名与 HTTPS
正式环境：
- app.example.com：教师/学生 Web。
- api.example.com：API。
- cdn.example.com：静态资源（可选）。

全站 HTTPS。

## 9. 环境
至少：
- local
- staging
- production

生产数据库/对象存储与测试环境隔离。

## 10. Secret
数据库密码、JWT/Session Secret、AI Key、对象存储 Secret 全部使用环境变量或云 Secret Manager。

`.env` 不提交 Git。

## 11. 备份
PostgreSQL：自动每日备份 + 时间点恢复能力（条件允许）。
对象存储：根据业务价值开启版本控制/生命周期策略。

定期做恢复演练，而不只是“开启备份”。

## 12. 监控
至少监控：
- API 5xx。
- p95/p99 延迟。
- CPU/RAM。
- DB 连接数和慢查询。
- Worker 队列积压。
- AI Job 成功率/耗时。
- 对象存储/CDN 流量。
- 前端 JS 错误。

## 13. 日志
结构化 JSON 日志；带 requestId/jobId。

避免写入密码、token、完整敏感教材原文。

## 14. 扩容判断
增加应用实例前先确认瓶颈：
- CPU 高：增加实例或优化计算。
- DB 慢：索引/查询/连接池。
- 媒体慢：CDN/对象存储。
- AI 慢：Worker 和 Provider 限流。

## 15. 是否需要 K8s
早期不需要。

当出现：多服务、多 Worker、频繁扩缩容、团队有成熟 DevOps 时再评估 Kubernetes。不要为了“企业级”标签增加不必要复杂度。

## 16. 成本控制
AI 成本：按 tenant/job 记录 token/调用成本。
存储成本：图片压缩、视频转码、生命周期清理。
CDN 成本：设置合理缓存。
日志成本：保留周期和采样。

## 17. 发布与回滚
每次生产发布对应不可变版本；保留上一稳定版本。一旦新版本出现严重错误，可快速回滚 Web/API。

数据库 migration 需要前后兼容策略，避免代码回滚后数据库不可用。
