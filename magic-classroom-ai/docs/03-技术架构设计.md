# Magic Classroom AI — 技术架构设计

## 1. 架构目标
技术架构需要同时满足两个阶段：
- 第一阶段：快速完成可演示 Demo。
- 第二阶段：平滑升级为可供学校实际使用的产品，而不是推倒重写。

核心原则：前后端分离、配置驱动、模板化、版本化、低耦合、可观察、可扩展。

## 2. 推荐技术栈
### Web 前端
- React
- Vite
- TypeScript
- React Router
- Zustand
- Framer Motion
- Tailwind CSS 或 CSS Variables + 组件级样式

### API 后端
MVP 推荐 FastAPI 或 NestJS 二选一。团队 Python 更熟悉则用 FastAPI；团队 TypeScript 更熟悉则用 NestJS。不要同时维护两套后端。

### 数据层
- PostgreSQL：主业务数据库。
- Redis：第二阶段按实际缓存/任务队列需要接入。
- S3 兼容对象存储：图片、音频、视频、用户上传文件。

### AI 层
通过统一 AI Provider Adapter 抽象接入模型，不让课程业务层直接依赖某一家模型供应商。

## 4. 前端工程结构
推荐正式阶段：
```text
apps/
  web/

  course-schema/
  ui/
  shared/
```

Demo 阶段可先单应用，但目录预留清晰边界。

### web/src
- app：应用启动、路由、provider。
- pages：路由级页面。
- course-engine：课程播放器核心。
- templates：课程模板。
- features：课程编辑、认证等业务模块。
- components：通用组件。
- store：全局状态。
- types：临时类型；稳定课程 Schema 后迁移至共享包。

## 5. Course Engine
Course Engine 是产品核心，不应和某一门英国课程耦合。

职责：
- 加载 CourseConfig。
- 校验 schemaVersion。
- 场景模板解析。
- 管理当前场景。
- 计算进度。
- 管理局部奖励/得分。
- 统一音频状态。
- 记录学习事件。
- 场景异常 fallback。

核心接口建议：
```ts
interface SceneRendererProps {
  scene: SceneConfig;
  course: CourseConfig;
  context: CourseRuntimeContext;
  onComplete: (result?: SceneResult) => void;
  onNavigate: (target: SceneNavigationTarget) => void;
}
```

## 6. Scene Registry
禁止在主播放器出现大量 if/else。

```ts
const sceneRegistry = {
  intro: IntroScene,
  'map-explore': MapExploreScene,
  timeline: TimelineScene,
  reading: ReadingScene,
  quiz: QuizScene,
  matching: MatchingScene,
  summary: SummaryScene,
  result: ResultScene,
};
```

新增模板时扩展 registry，而不是复制播放器。

## 7. 状态管理
分三层：
- Server State：课程、用户、发布版本，后续使用请求缓存库管理。
- App State：登录状态、UI 偏好。
- Course Runtime State：当前场景、临时得分、音频、任务完成状态。

避免所有状态都塞进 Zustand。

## 8. 数据版本化
CourseConfig 必须包含 schemaVersion。

```json
{
  "schemaVersion": "1.0",
  "courseId": "magic-journey-britain",
  "version": 1,
  "scenes": []
}
```

后续 Schema 升级通过 migration/adapter 兼容旧课程。

## 10. API 风格
REST 优先，第一版不要为了形式引入 GraphQL。

示例：
- POST /auth/login
- GET /courses
- POST /courses
- GET /courses/{id}
- POST /courses/{id}/versions
- POST /courses/{id}/publish
- POST /assets/upload-url
- POST /generation-jobs
- GET /generation-jobs/{id}

统一响应错误：code/message/requestId/details。

## 11. 数据库原则
- UUID/ULID 作为业务主键均可，项目统一一种。
- 所有核心表有 created_at/updated_at。
- 多租户表包含 tenant_id 并建立索引。
- Published CourseVersion 不原地修改。
- 课程配置可用 JSONB，但关键检索字段需独立列。

## 12. AI Job 架构
AI 生成属于异步任务。

```text
HTTP request -> create GenerationJob -> queue -> worker -> model -> validate -> persist -> status update
```

不要保持 HTTP 请求等待几分钟。

必须：
- idempotency
- timeout
- limited retry
- failure reason
- model/prompt version tracking
- cost metadata

## 13. 文件上传
推荐前端向服务端申请 presigned URL，再直传对象存储。

服务端保存 Asset 元数据。

禁止：
- 大文件先全部经过应用服务器内存中转。
- 把对象存储长期访问密钥发送给前端。

## 14. 安全
- 所有生产 secret 使用环境变量或 Secret Manager。
- 密码使用成熟密码哈希库。
- 登录和 AI 生成接口限流。
- 服务端执行租户与资源 owner 权限校验。
- 上传文件验证 MIME/大小。
- 对富文本进行 XSS 防护。
- CORS 使用明确白名单。
- 不把用户原始敏感材料写进普通应用日志。

## 15. 性能
课程播放器目标是素材重型页面，因此关键在资源策略：
- 首场景仅加载首屏关键资源。
- 下一场景可 idle 预取。
- 图片响应式尺寸。
- 静态素材 CDN。
- 视频流媒体化，不直接打包进 JS。
- 动画优先 transform/opacity。
- 粒子数量随设备能力降级。

## 16. 服务器演进
### Demo
纯静态部署，无需独立服务器。

### 单校 MVP
API 4vCPU/8GB 可作为起点，但真实规格应依据监控与压测；数据库和对象存储尽量使用托管服务。

### 多校
应用层水平扩展，DB 独立，Redis/队列独立，对象存储 + CDN。

### SaaS
负载均衡、自动扩缩容、任务 Worker 池、数据库高可用、备份、监控告警。不要在用户量尚小时提前引入 K8s 复杂度。
