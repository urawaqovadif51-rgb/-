# 23. 数据库迁移与初始化规范

## 1. 工具
正式后端使用 SQLAlchemy + Alembic 管理 PostgreSQL schema 迁移。

## 2. 原则
- 所有 schema 变更必须通过 migration，不允许直接手改生产数据库。
- migration 文件进入 Git。
- migration 尽量保持可回滚。
- 大表高风险变更分阶段执行，避免长时间锁表。
- 生产环境迁移前必须备份并验证回滚路径。

## 3. 推荐目录
```text
apps/api/
├── alembic.ini
├── alembic/
│   ├── env.py
│   ├── script.py.mako
│   └── versions/
└── app/
    └── db/
        ├── base.py
        ├── session.py
        └── models/
```

## 4. 初始 migration 顺序
1. tenants
2. users
3. courses
4. course_versions
5. scenes
6. assets
7. templates
8. generation_jobs
9. learning_sessions
10. interaction_records
11. rewards

## 5. 基础字段
业务表优先包含：
- `id UUID PRIMARY KEY`
- `created_at TIMESTAMPTZ`
- `updated_at TIMESTAMPTZ`
- 多租户表包含 `tenant_id`

需要软删除的表增加：
- `deleted_at TIMESTAMPTZ NULL`

## 6. 索引
至少考虑：
- users(tenant_id, email)
- courses(tenant_id, status, updated_at)
- courses(slug)
- scenes(course_version_id, order_index)
- assets(tenant_id, course_id, type)
- generation_jobs(tenant_id, status, created_at)
- learning_sessions(course_id, user_id, created_at)
- interaction_records(session_id, created_at)

不要给低选择性字段盲目增加独立索引。

## 7. 唯一约束
- 用户邮箱应按租户策略决定全局唯一或 `(tenant_id, email)` 唯一。
- 发布 slug 全局或租户内唯一，产品确定前先采用租户内唯一。
- scene order 在同一 course_version 下应避免重复。

## 8. Migration 命名
格式示例：
`20260818_001_create_core_tables.py`

Revision message 必须描述业务变化，禁止 `update db` 这种模糊名称。

## 9. 数据种子
开发环境可以提供 seed：
- 1 个 demo tenant
- 1 个 teacher
- 1 个 student
- Britain 示例课程
- 默认模板 registry

生产 seed 不得创建弱密码演示账号。

## 10. Codex任务要求
Codex 每次新增/改表时必须：
1. 修改 SQLAlchemy model。
2. 生成/编写 migration。
3. 检查 upgrade/downgrade。
4. 增加相关测试。
5. 说明是否需要数据回填。

## 11. 上线迁移流程
备份 → staging 演练 → migration dry review → 维护窗口/灰度 → upgrade → 健康检查 → 关键查询校验 → 发布应用。

如果数据库迁移失败，优先停止应用发布并回滚，而不是继续带病运行。
